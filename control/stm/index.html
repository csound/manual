    State Machine Graphs

    The STM opcodes build state machines as graphs of named nodes connected by directed edges. The graph decides which node is current and which moves are allowed; what a node does is ordinary orchestra code. The design is inspired by LangGraph.

    Use them for anything that moves through distinct stages: the sections of a piece, the phases of a gesture, the modes of an interactive patch, or a voice that switches between processes.

    Builder, definition and runner

    A graph goes through three objects, each referred to by a numeric handle:

    1. stmcreate returns a builder. Add nodes with stmaddnode, edges with stmaddedge or stmaddcondedge, and optionally choose the entry node with stmentry.
    2. stmcompile freezes the builder into an immutable definition. After that the builder cannot be changed.
    3. stminstance creates a runner from a definition. The runner holds everything that changes during performance: the current node, the pending request, the clock and the event history. One definition can back any number of runners, each fully independent.

    All three are i-time opcodes. Every other STM opcode takes a runner handle.

    builder:i = stmcreate()
stmaddnode(builder, "Calm")
stmaddnode(builder, "Build")
stmaddnode(builder, "Burst")
stmaddedge(builder, "Calm", "Build")
stmaddedge(builder, "Build", "Burst")
stmaddcondedge(builder, "Burst", ["Calm", "Build"])
gi_definition@global:i = stmcompile(builder)

    Lifetime of the handles

    A builder, definition or runner belongs to the opcode instance that created it, and its handle is removed when that instance ends. Created in the global space, outside any instrument, it lasts for the whole performance. Created in an instrument, it lasts as long as that note.

    Opcodes that already use a runner keep it alive after its handle is removed, and a runner keeps its definition alive in the same way. An opcode that is initialized with a removed handle reports an initialization error.

    The runtime loop

    In each control period, the orchestra asks the runner for the current node, runs the code for that node, and then calls stmadvance:

    node:S = stmcurrent(r)
if strcmpk(node, "Calm") == 0 then
  CalmNode(r, state)
elseif strcmpk(node, "Build") == 0 then
  BuildNode(r, state)
else
  BurstNode(r, state)
endif
status:k, from:k, to:k = stmadvance(r)

    A node asks for a move with stmnext. The request is not applied at once: stmadvance checks it against the edges of the current node, applies it if the edge exists, and reports the outcome. A common pattern is to write each node as a UDO that receives the runner handle and a shared struct by reference, so that nodes communicate through the struct and the sound is computed from it.

    stmcurrent gives the current node by name and stmcurrentid by id. Ids are numbers from 0, assigned in the order the nodes were added. stmnodeid, stmnodename, stmnodecount and stmedgecount translate between names and ids and describe the graph.

    Advance status

    stmadvance returns a status, the id of the node it started from and the id of the requested node:

    Status Meaning
    0 No request was pending.
    1 The request was legal and the runner moved to another node.
    2 The current node has no edge to the requested node. Nothing changed.
    3 The request was a legal self edge: the runner stays on the same node, but the move counts as a transition.
    4 Two different nodes were requested in the same control period. Neither is applied.
    5 The runner is paused.
    6 The runner is deleted.

    The target id is -1 when no single node was requested, and when the runner is paused or deleted.

    Requests share one pending slot. Repeating the same request is harmless. Requesting a different node before stmadvance makes the advance report a conflict (status 4) and apply neither request.

    Watching transitions

    stmonenter and stmonexit output 1 when a named node has just been entered or left. They are meant for starting and stopping processes when the graph moves, for example scheduling an instrument when a node is entered and releasing it when the node is left. They only see the most recent transition, so they should run in every control period, ideally in the same instrument that advances the graph.

    stmevent reads the runner's event history in order: transitions, resets, recalls, pauses, resumes and deletion. The runner keeps the last 10 events, and each stmevent reports when it has missed some.

    The graph clock

    Each runner has its own clock, read with stmtick, stmtime and stmnodetime. The clock is moved by stmadvance, one control period per call, so it only runs while the machine is being stepped. It stops while the runner is paused, and it does not follow performance time when the driving instrument is not running.

    Two rules follow:

    • Call stmadvance once per control period for each runner.
    • Read the clock before stmadvance. After it, the clock already shows the values for the next control period.

    The clock counts in integers, so it does not drift over long performances. Each advance adds the length of the control period of the instrument or UDO that calls it, including local setksmps, oversample and undersample settings.

    Controlling a runner

    • stmreset returns the runner to its entry node and restarts its clock.
    • stmpause and stmresume freeze and release the runner. While it is paused, requests are ignored and the clock stops.
    • stmdelete stops the runner for good.
    • stmcall saves the state of the runner under a name, and stmrecall restores it. A name works as a save slot: saving it again replaces the previous state.

    All six take a trigger and act when it becomes positive. Holding the trigger high does not repeat the action.

    Writers and observers

    Opcodes that change a runner are writers: stmnext, stmadvance, stmreset, stmpause, stmresume, stmdelete, stmcall and stmrecall. A runner accepts writers from one instrument instance at a time, including the UDOs it calls. If another instance tries to initialize a writer while the first is active, it gets an initialization error. When the first instance ends, another can take over.

    All other runtime opcodes are observers. Any number of instruments can observe a runner at the same time, including with the multicore engine.

    • stmcurrent

    Examples

    • stm.csd: the runtime loop, with one UDO per node and a shared struct.
    • stm-trace.csd: every advance status, ids, the clock and a reset.
    • stm-events.csd: enter/exit triggers and the event history, with pause, resume and delete.
    • stm-checkpoint.csd: saving and restoring the state of a runner.
    • stm-processes.csd: nodes bound to instruments, and two runners sharing one definition.
